DataMind

A local-first, self-correcting, RAG-augmented multi-agent framework for autonomous exploratory data analysis. It profiles a dataset, has an LLM propose research questions, writes and repairs analysis code inside a network-isolated Docker sandbox, and turns verified output into grounded insights, charts and a PDF report. It is also a controlled testbed: every pipeline stage is logged so the effect of retrieval (RAG vs. baseline) can be measured, not guessed. Evaluated on 24 paired datasets and 322 end-to-end trials.

01 / Project Overview

What DataMind does

DataMind takes a raw dataset from upload to explained insight with minimal human input, while doubling as a controlled research testbed comparing RAG-augmented vs. baseline question generation.

📁Upload & Profile

CSV, TSV, JSON, Excel or Parquet via upload, URL, Kaggle or GitHub. A pandas profile (schema, nulls, stats, correlations, 10 sample rows) is the only thing the LLM sees; raw data never leaves the machine.

🧠Autonomous Questioning

One LLM call per dataset proposes research questions across six categories (data cleaning, distribution, correlation, trend, anomaly, segmentation). A gatekeeper scores each 1–5 and drops anything below 3.

🔁Self-Correcting Analysis

Per question, a LangGraph state machine writes code, runs it in Docker, reads the traceback on failure and rewrites it (3-attempt budget). Self-correction lifts success from 82.0% to 99.1%.

🔎Switchable RAG

Schema-similarity retrieval (k=5) over past insights feeds question generation only. One on/off switch makes RAG the single experimental variable.

📄Insights, Charts, Report

Numerically grounded insights, up to three chart specs, a system-profile dashboard, a cleaned-dataset export and a Puppeteer-rendered executive PDF report.

📊Measured Per Stage

Immutable per-trial JSONL telemetry plus offline LLM-judge scoring grade the questions, code, insights and token cost, not just the final answer.

02 / System Architecture

FastAPI backend, Next.js frontend, local-first AI stack

A LangGraph agent graph owns the reasoning loop, a FastAPI service layer owns persistence and orchestration, and a local ChromaDB store provides zero-cost RAG grounding — sandboxed in Docker for untrusted code, with Gemini as the supported LLM provider.

Presentation / Orchestration Transport / Persistence Sandbox / Realtime RAG LLM provider layer

🧭 The one architectural rule the codebase enforces

question_generator is deliberately kept outside the per-run LangGraph graph — it runs once per dataset, while the compiled graph (code_generator → sandbox_execute → result_analyzer → insight_writer → visualization_builder, with a code_corrector retry loop) runs once per research question. This keeps "generate N questions" state from ever mixing with "answer 1 question" state. All categories, including the system_profile dashboard question, go through code_generator and the sandbox with no bypass.

03 / Data Flow

Dataset lifecycle, end to end

The canonical path a dataset travels from upload to a downloadable report.

STEP 1

Upload & Ingest

A CSV/JSON file is uploaded, or fetched via direct URL / the Kaggle API through the Dataset Fetch Service. The raw file is persisted and a Dataset row is created.

STEP 2

Profiling

The profiling service computes a schema summary, stats summary, correlation summary and sample rows — metadata only, never raw rows beyond a bounded sample — stored as a DatasetProfile.

STEP 3

Research Question Generation

question_generator calls the LLM once per dataset to produce a batch of dataset-specific questions, spread over six categories (data cleaning is mandatory when nulls or extreme outliers exist), each with target columns, expected output type and rationale. RAG can ground the call with insights from similarly-shaped past datasets (the query dataset itself is excluded). rq_quality_scorer then rates each question 1–5 and drops those below 3.

STEP 4

Per-Question Analysis Run

For each selected ResearchQuestion, an AnalysisRun starts the LangGraph pipeline: code_generator writes pandas code from the question + profile context.

STEP 5

Sandboxed Execution & Self-Correction

sandbox_execute runs the code in a fresh Docker container (--rm --network none, 1 GB / 1 CPU, read-only script and data, 60 s timeout; subprocess mode is for dev only). On failure, code_corrector rewrites the code using the traceback and loops back to execution — until success or max_attempts is exhausted, at which point the run is marked failed.

STEP 6

Result Analysis

result_analyzer is a deterministic (non-LLM) node that truncates/sanitizes stdout so downstream LLM calls get clean, bounded input — logic kept in one place instead of duplicated across nodes.

STEP 7

Insight Writing & Visualization

insight_writer turns the execution output into a narrative Insight. visualization_builder asks the LLM only for chart metadata (type/title/labels) — the PNG itself is rendered by the sandboxed script per the code-generator's contract (./output/chart.png) — and is skipped entirely if no chart was produced.

STEP 8

RAG Indexing (best-effort)

On a successful run, the new insight is written into the local Chroma vector store by the RAG indexer, keyed on the dataset's "schema text" embedding — so future datasets with a similar shape can retrieve it. Indexing failure never fails the run itself.

STEP 9

Report & Export

A structured markdown Report (per-category sections, numbered findings, key takeaways) is generated and exported as an A4 PDF by a server-side Puppeteer route, alongside the cleaned dataset and a before/after cleaning comparison. Every run also appends one record to trials.jsonl (experiments) or app_trials.jsonl (app use).

04 / Supported Modules & Agent Nodes

7 graph nodes plus 2 pre-graph agents

Each node is a focused async function operating on a shared AnalysisState TypedDict — LLM-calling nodes load their system prompt from a dedicated markdown file under app/agents/prompts/.

01

question_generator

Runs once per dataset (not per run), invoked directly from POST /datasets/{id}/questions. Produces a structured ResearchQuestionBatch split into Pre-processing and EDA categories, each tagged with target columns and rationale.

01b

rq_quality_scorer

Gatekeeper called right after generation. One structured LLM call scores every question 1–5; questions below 3 are dropped in both experiment arms.

02

code_generator

First node of the per-run graph. Writes pandas analysis code for one research question, using dataset profile context (schema/stats/correlation summaries + sample rows) and, optionally, retrieved similar past insights.

03

sandbox_execute

Runs the latest generated code in the sandbox (services/sandbox.py; Docker with --network none, --cap-drop ALL, no-new-privileges, tmpfs /tmp) against the real dataset file, capturing stdout/stderr, exit code, duration and any produced output files (e.g. chart.png).

04

route_after_execution (conditional edge)

Branches on the execution result: success → result_analyzer; failure with attempts remaining → code_corrector; attempts exhausted → give_up, which marks the run failed and stores the last stderr.

05

code_corrector

Given the failing code and its traceback, asks the LLM for a corrected version, appends it to code_history, and loops back to sandbox_execute — the self-correction retry loop, bounded by max_attempts.

06

result_analyzer

Deterministic, no LLM call. Truncates the successful execution's stdout to a bounded size so both insight_writer and visualization_builder receive clean input without duplicating that logic.

07

insight_writer

Writes a brief summary, key takeaways and a confidence score from the question, cleaned output and profile stats, forbidden from using numbers absent from stdout. Requires non-empty stdout.

08

visualization_builder

Asks the LLM only for structured chart metadata (type, title, axis labels) describing a chart the sandboxed script already rendered to disk; the node is skipped entirely when no chart file was produced.

09

RAG store (ChromaDB, local)

A local persistent Chroma client (no server) with all-MiniLM-L6-v2 embeddings, so indexing and retrieval cost zero API tokens. An RLock guards client initialization against concurrent crashes.

10

RAG retriever

Embeds the target schema text and returns the top-5 most similar past records (question, summary, category) by cosine similarity, excluding the query dataset. An audit confirmed 0.0% leakage. Used only as inspiration, never for copying columns or numbers.

11

RAG indexer

Writes each completed insight into the local store right after its AnalysisRun succeeds and commits. Best-effort by design — a failure here must never fail the run itself.

12

Dataset Fetch Service

Handles ingestion from a direct URL or the Kaggle API, normalizing both into the same on-disk raw-dataset representation the rest of the pipeline expects.

13

LLM Provider Factory

A single get_llm factory taking per-node provider:model specs (default google:gemini-3.1-flash-lite, temperature 0.2). Wraps calls in tenacity retry and counts rate-limit retries. Gemini is the supported path; OpenRouter exists as an undocumented secondary.

🔐 Auth

Local single-user login with a JWT session; startup refuses a weak secret outside development.

📡 Live Status

A token-authenticated WebSocket fed by an in-process pub/sub bus pushes run status; the UI also auto-polls and stops once the pipeline completes.

📊 Run Metrics

RunMetrics plus per-node token and call breakdowns and rate-limit retry counts feed the RAG-vs-baseline comparison.

🧹 Cleaned Export

Cleaned CSV download, before/after null comparison, charts as PNGs and an executive PDF report.

08 / Evaluation Framework

Grading every stage, not just the answer

A paired design: 24 datasets, 2 arms (Baseline vs RAG), 48 question batches, 322 end-to-end trials. Same model (gemini-3.1-flash-lite), temperature 0.2, 3 attempts, 60 s timeout. Retrieval is confined to question_generator, so it is the only variable.

❓ Question quality

Column grounding, category coverage, redundancy (cosine > 0.80) and semantic diversity, computed automatically. Relevance, specificity and actionability (1–5) come from an offline LLM judge.

💻 Code quality

FPSR, ESR, mean attempts, latency, static signals (complexity, .iterrows(), guard clauses, syntax) and a 5-dimension rubric (0.20 weight each).

💡 Insight and cost

Numerical faithfulness, takeaway groundedness, Flesch–Kincaid readability, caveat coverage, tokens per successful insight, LLM calls, latency and a failure taxonomy.

🧪 Method details

Datasets were sampled from a catalogue of 134 public Kaggle/GitHub sets across 29 domains (569 to 32.4M rows, 4 to 40 columns). The vector store held 78 deduplicated insights and was frozen during runs. Tests are two-sided Wilcoxon signed-rank on per-dataset means (n=24), Holm–Bonferroni across 29 metrics, with 95% bootstrap CIs (B=10,000). Judging is offline over the append-only log, so it adds no live cost. Reproduce with seed_datasets.py → experiment.run_experiment → judge_trials → analyze_results.

H1 · Not supported

RAG scored higher on average, but no difference survived correction. Relevance improved on 11 of 24 datasets (tied 8, lower 5); effects are small (dz 0.24–0.28).

H2 · Holds on cost

The token increase is small and prompt-driven (question generation +4.2%, insight writing +13.5%), but no quality gain offsets it.

H3 · Partly supported

Retrieval did not hurt grounding or faithfulness, and self-correction recovered most failures, but retrieval significantly lowered first-pass success.

⚠ Limitations and future work

The judge shares a model with the generator and has no human calibration. With n=24, one batch per arm and no repeats, tests are underpowered. Generalisation is limited by 24 public datasets, a 78-insight seed corpus and one low-cost model; the 1 GB / 60 s sandbox strains the largest sets (two Bitcoin first attempts timed out, then self-corrected). Next: retrieve successful code snippets, add human review of questions, and test stronger models, multi-table data and multiple judges.
